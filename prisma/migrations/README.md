## How to Apply Migrations

### Option 1: Using the Migration Script (Recommended)

```bash
npm run migrate:production
```

This interactive script will:
- Check your database connection
- Show current database state
- Ask for confirmation
- Apply all pending migrations
- Verify the migration succeeded

### Option 2: Using Prisma CLI Directly

```bash
# Apply all pending migrations to production
npx prisma migrate deploy

# Apply migrations in development (creates migration history)
npx prisma migrate dev
```

### Option 3: Manual SQL Execution

If you prefer to run SQL directly:

1. Find the migration SQL file: `20241209000000_init_production_schema/migration.sql`
2. Execute it in your database using your preferred tool (psql, Supabase dashboard, etc.)
3. Record the migration in Prisma's history (see DATABASE_MIGRATION.md for details)

## Migration Files

Each migration directory contains:
- `migration.sql` - The actual SQL to execute
- Migration metadata (automatically generated by Prisma)

## Best Practices

1. **Always backup before migrating:** `pg_dump your-db > backup.sql`
2. **Test on staging first:** Apply migrations to a test database before production
3. **Never edit migration files:** They should be immutable once created
4. **Use version control:** All migrations are tracked in git
5. **Deploy migrations separately:** Run migrations before deploying new code

## Troubleshooting

If you encounter issues, see the comprehensive troubleshooting guide in:
- [DATABASE_MIGRATION.md](../../DATABASE_MIGRATION.md)

Common issues:
- **"Table already exists"** - Tables were partially created; see rollback procedures
- **"Connection timeout"** - Check your DATABASE_URL and network connectivity
- **"Permission denied"** - Your database user needs proper permissions

## Environment Variables

Migrations use these environment variables:

- `DATABASE_URL` - Primary connection string (must NOT use connection pooling for migrations)
- `DIRECT_DATABASE_URL` - Optional direct connection (bypasses pooler)

**Important:** For migrations, use a direct database connection, not a pooled connection:
- ✅ Good: `postgresql://user:pass@host:5432/db`
- ❌ Bad: `postgresql://user:pass@host:6543/db?pgbouncer=true`
