# Clinical Library – Deep Audit & Execution Plan

## Scope

The **Clinical Library** is the **Condition Library** tab inside the Knowledge Base (`/study/knowledge` → tab "Condition Library"). It is implemented by [components/library/ClinicalReferenceLibrary.tsx](components/library/ClinicalReferenceLibrary.tsx), which uses [components/knowledge/KnowledgeBaseHub.tsx](components/knowledge/KnowledgeBaseHub.tsx). Data comes from `MedicalContent` (Prisma) via `/api/content/library` and `/api/content/systems`; the detail slide-over uses [SmartConditionView](components/library/SmartConditionView.tsx) (lazy-loaded) with data from `/api/content/condition/:conditionId/summary` and `/details`.

---

## 1. Database Structure & Normalization

### 1.1 Current State

- **Dual models:** [Condition](prisma/schema.prisma) (id, name, system, content Json?, …) and [MedicalContent](prisma/schema.prisma) (conditionId @unique, system, subcategory, condition, 40+ text/Json fields). Library reads **MedicalContent** only; [functions/api/conditions/[identifier]/extended.ts](functions/api/conditions/[identifier]/extended.ts) still uses the deprecated Condition table.
- **Content shape:** MedicalContent mixes strings, stringified JSON arrays, and real JSON in fields like `buzzwords`, `clinical_pearls`, `classic_triad`, `symptoms`, `complications`, `differentials`, `physicalExam` (camelCase in schema) vs `physical_exam` in [lib/utils/normalization.ts](lib/utils/normalization.ts) (textFields). Inconsistent naming (e.g. `riskFactors` vs `risk_factors`) and mixed types force heavy client-side parsing.
- **Full-text search:** [functions/api/content/library.ts](functions/api/content/library.ts) uses `search_vector @@ websearch_to_tsquery`. If `search_vector` is null for some rows (e.g. before trigger backfill), FTS fails and the API falls back to LIKE on a few fields.
- **Normalization:** [lib/utils/normalization.ts](lib/utils/normalization.ts) and [lib/utils/jsonParser.ts](lib/utils/jsonParser.ts) handle stringified JSON and “fake nulls”; [normalizeMedicalContent](lib/utils/normalization.ts) uses `physical_exam` and `riskFactors` in textFields but does not include all MedicalContent field names (e.g. `physicalExam` camelCase). Schema uses both styles across fields.

### 1.3 Blockers & Debt

- **Condition vs MedicalContent:** Extended condition API and any code still using the Condition table for “content” should migrate to MedicalContent or be clearly deprecated; [functions/api/conditions/[identifier]/extended.ts](functions/api/conditions/[identifier]/extended.ts) states it “should migrate to MedicalContent”.
- **search_vector nulls:** If many rows have null `search_vector`, library search will fall back to LIKE and may be slow or incomplete; backfill is a prerequisite for reliable search.

## 2. Library Interface – Steps to Finish the UI

### 2.1 Current State

- **Flows:** Systems and subcategories load from `/api/content/systems` and client-side grouping; content from `/api/content/library`. Detail panel uses `SmartConditionView` with `conditionId` (lazy load via summary + details APIs). Breadcrumb, sidebar, high-yield filter, and keyboard nav (/, Esc, arrows) are implemented.
- **Search:** Two paths: (1) non-empty search uses `useSemanticSearch` (RAG/embedding) and shows semantic results + optional one-sentence answer; (2) when search is empty, filtered list from `/api/content/library`. Sidebar search input and header search both set `searchQuery`; in non-search mode the library also filters `filteredContent` by `searchQuery` (client-side filter on condition, classic_patient, buzzwords). So with search text, semantic results are shown; with no search, library API + client filter. Clarify or unify behavior (e.g. whether header search should trigger semantic vs FTS).
- **Response handling:** Library API returns `{ data: { content, count } }`; middleware serializes with `result.data`, so response body is `{ content, count }`. Client correctly uses `parsed.content` ([ClinicalReferenceLibrary.tsx](components/library/ClinicalReferenceLibrary.tsx) ~line 190).

## 4. Design System – Stormy Slate and Accent (#7a6f52)

### 4.1 Current State

- **Tokens:** [index.css](index.css): light theme `--color-accent: #64748b` (slate), dark `--color-accent: #94a3b8`. `--color-accent-border` uses gold-ish values (`#9a8f72` light, `#c4b78a` dark). [tailwind.config.js](tailwind.config.js) exam-mode utility sets `--color-accent: #7a6f52` (darker gold). So the **default** theme uses slate for accent; **darker gold (#7a6f52)** is only in exam-mode and in docs ([CONTRAST_RATIO_IMPROVEMENT_PLAN.md](docs/CONTRAST_RATIO_IMPROVEMENT_PLAN.md), [AUDIT_FIXES_STEP4_STEP5.md](AUDIT_FIXES_STEP4_STEP5.md)).

## 6. Priority Order and Blockers

**Recommended order:**

1. **Database & content (Section 1):** Backfill search_vector (1.2.4), then canonical field list and normalization (1.2.1, 1.2.2), then optional Zod/typing (1.2.3) and content cleanup (1.2.5). This unblocks reliable search and consistent parsing.
2. **Library UI (Section 2):** Unify search (2.2.1), then empty/error and detail loading (2.2.3, 2.2.4), then pagination/virtualization (2.2.2) and URL state (2.2.5).
3. **Partially coded features (Section 3):** Consolidate BookmarksPanel and add bookmarking to library (3.1); then Recent, QuickQuiz, DDx/Confusion, and keyboard help; then remove or use ConditionMasterEmbedded.
4. **Design system (Section 4):** Decide accent (4.2.1), then audit library components (4.2.2, 4.2.3).
5. **Clean-up (Section 5):** Remove or repurpose MedicalContentBrowser, delete ToolkitHub.bak, trim dead code in ClinicalReferenceLibrary, resolve LibraryCard and docs.

**Immediate blockers:**

- **search_vector nulls:** Can make library search unreliable until backfilled.
- **Condition vs MedicalContent:** Confusion and duplicate code paths until extended API and any Condition-based content are deprecated or migrated.
- **Response shape:** Confirmed that library API response is `{ content, count }` and client reads `parsed.content` correctly (no change needed).
